## 一、B1 复核：语义足够，缺一张「settle 结论 → 闸门动作」表

### 已写对的部分

- 「`schedulePush()` 只置 dirty 不发 PUT」——切口选得准，dirty 仍然落盘，离线记账的数据安全不受影响。
- 「settle 成功后统一放闸，若仍 dirty 再补推一次」——补推用 `getLocalVersion()`，此时该值刚被 settle 校准过，语义干净。
- 「hydrate 失败 / 需重拉期间禁止推送」——把 P0-4 的杀伤面（残缺账本推成云端权威）堵死了。
- 「`online` 同受约束」——**意图对**（不能让 online 绕过闸门抢跑），但落地方式需要修正，见下。

### C1 · 缺口：settle 不成功时，闸门没有放开路径

settle 的结论不止「成功 / 失败」两种，M1' 本身就要返回 `hydrated` / `in-sync` / `conflict` / `offline` / `empty-cloud` / `auth-expired`。「settle 成功前不放闸」只覆盖了前三种里的两种。

**具体退化路径**：用户离线记 10 笔 → dirty 累积（正确）→ 恢复网络 → `online` 事件触发 → 按 B1 第 2 点「同样受闸门约束」→ 只置 dirty、不推 → 而闸门要等 settle 成功，**离线期间 settle 从未成功过，也没有任何东西会再触发一次 settle** → 这 10 笔要等到用户下次冷启动（关标签页重开）才上云。

在常驻标签页 / 手机上挂着不关的场景里，这个「下次冷启动」可能是好几天。数据不丢（dirty 落盘了，第一轮的 F1 不会复现），但**相对今天的行为是明确退化**——现状 `online` 是立刻补推的。

**修正很小：`online`（以及回前台）触发的应该是 re-settle，而不是 push。** settle 得出结论后自然会放闸补推，既不抢跑也不死锁。

建议把 B1 第 1、2 点替换成这张表（同时就是 M1' 状态机的验收表）：

| settle 结论 | 闸门 | dirty 处理 |
|---|---|---|
| `in-sync`（版本一致） | **放开** | 若仍 dirty → 补推 |
| `hydrated`（以云为准合入） | **放开** | hydrate 已 `clearDirty()`，无需补推 |
| `empty-cloud`（云 404 且本机有数据） | **放开** | 补推（P1-3，带 B4 身份前置） |
| `conflict`（dirty + 云端更新） | **保持关闭** | 等用户选择；**冲突解决路径显式豁免闸门**（见下） |
| `offline` / 超时（P0-5） | **保持关闭** | 继续累积 dirty；`online` / 回前台 → **re-settle**，不直接 push |
| `auth-expired` | **保持关闭** | 继续累积 dirty；重新登录后 re-settle |
| hydrate 失败 / 需重拉 | **保持关闭** | 只置 dirty；直到一次成功 hydrate 或用户显式选择 |

### C1 附带的三个实现级要点（写进 S1' 验收即可）

1. **闸门的检查点要落在 `runPush()` 入口，不能只在 `schedulePush()`。** `runPush` 失败时会排一个 30s 的 `retryTimer`（`cloudSync.js:163-166`），这个已排下的 timer 到点会**直接调 `runPush()`**，绕过 `schedulePush()`。只在 `schedulePush()` 里判闸，这条路径会漏。
2. **冲突解决路径必须显式豁免。** `resolveConflictUseLocal()` / `resolveConflictUseCloud()` 是直接调 `pushRemote()` / `fetchRemote()` 的，不走 `schedulePush()`——今天天然不受影响。但要在方案里写明「这是用户显式决定，豁免闸门」，否则实施时若把闸门下沉到 `pushRemote()` 层，冲突窗会变成点了没反应。
3. **闸门是内存态，不持久化。** 页面刷新即回到关闭，正确；dirty 本身是落盘的，不受影响。另外 `resetSyncState()` 目前会 clearTimeout 两个 timer，要顺带定义它对闸门的影响（建议：一并关闭）。

## 二、B2 复核：四格正确，但漏了第五格

### 四格判断

| 格 | 判定 |
|---|---|
| 不进 `ALL_CLEARABLE_KEYS` | ✅ 正确，且**这是唯一真正产生保护的一格** |
| 不进 `collectLedgerData` / 云 payload | ✅ 正确（`collectLedgerData` 遍历的就是 `ALL_CLEARABLE_KEYS`，第一格成立则自动成立） |
| 不进 patch 的 dirty 白名单 | ✅ 正确（`initSync` 的白名单也是 `ALL_CLEARABLE_KEYS`，同上） |
| 列入 `PRESERVED_ON_RESET` / 保留键清单 | ✅ 正确，但要知道它是**登记性质**——`storageKeys.js:77` 的注释写得很清楚「文档用，供检查」，`clearAllData()` 并不读这张表 |

补一句认识：**这四格实质是「一格 + 三个推论」**。`ALL_CLEARABLE_KEYS` 一张表同时充当清除清单、备份范围、云 payload 范围、patch 白名单四个角色，所以实施要点只有一条——**任何人不得因为任何理由把 `pam-cloud-bound` 加进这张表**。写全四格是好事（把推论显式化，避免误判），但别让「已经加进 PRESERVED 了」产生虚假的安全感。

### C2 · 漏掉的第五格：`resetSyncState()`

`resetSyncState()`（`cloudSync.js:283-290`）**不读 `ALL_CLEARABLE_KEYS`**，它是硬编码的两行 `removeItem`：`pam-sync-meta`、`pam-sync-dirty`。而 M8 的清理流程要经过 `clearAllData()` → `resetSyncState()`。

于是：`pam-cloud-bound` 从命名到用途都和 `pam-sync-meta` 是同一类（本机同步元数据），实施时「顺手」在 `resetSyncState()` 里多加一行 `removeItem('pam-cloud-bound')` 是**极其自然的动作**——而这一行会让 P0-2(c) 全部失效，离线诱导建账那条丢账路径原样回来，且四格表全都拦不住它（因为四格管的是 `ALL_CLEARABLE_KEYS`，`resetSyncState` 根本不看那张表）。

**建议现在补进 B2 表**：

| 是否进入 | 结论 |
|---|---|
| `resetSyncState()` 清理范围 | **否**（它的全部意义就是在 version 被清零之后仍然记得「这台机器绑过云端账本」） |

### C2 附带两点（可并入 S4' 验收）

1. **谁写这个键**：方案没说。建议在 `setLocalVersion()` 同处更新（每次成功 settle / 成功 PUT），否则这个键永远为空，门闸判「曾绑定」时读到 null，P0-2(c) 同样落空。
2. **普通退出与安全退出对它的处理应当不同**：
   - **普通退出**：保留（"我还会回来"）——这是 P0-2(c) 的全部依据。
   - **安全退出**：建议清掉（"这台机器不属于我"）。secureLogout 的目标场景是公共电脑 / 借出设备，留一个 `{lastVersion, lastSyncedAt, emailHash}` 虽不是账本正文，但仍泄露"这台机器上有人用过 PAM、最后同步时间"。而且 secureLogout 会 `location.assign('/cdn-cgi/access/logout')` 结束 Access 会话，下次进来是完整的重新绑定流程，不需要这个标记。

   这个差异如果不写明，两条路径会被实施成同一个函数。
