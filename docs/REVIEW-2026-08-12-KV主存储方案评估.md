# PAM · v1.08.12「KV 主存储」方案独立评估（2026-08-12）

范围：`docs/PLAN-v1.08.12-KV主存储.md` 全文，对照当前代码事实（`src/utils/cloudSync.js`、`src/App.vue`、`src/main.js`、`src/utils/dataReset.js`、`src/stores/auth.js`、`src/composables/useIdleLogout.js`、`src/constants/storageKeys.js`、`functions/api/ledger/index.js`、`functions/api/_lib/accessJwt.js`）。
性质：**只读评估，未改动任何代码**。结论用于决定是否按 S1→S5 开干。

---

## 0. 总体判断

**方向批准，但方案本身不能按现在这版直接开干。**

「KV 权威 + localStorage 缓存/离线缓冲」这个心智模型是对的，不上 D1 也是对的——数据模型就是「一人一整本 JSON」，KV 与之同构，D1 的收益在这个体量上收不回迁移成本。继承整本协议、不重写 Pinia 写路径，是这版最聪明的取舍：真正翻转的只有**启动时刻谁说了算**，运行期仍是本地缓冲，改动面因此被压在同步层里。

问题不在方向，在**三条被方案当作「低风险」或「未必要改」而实际上是硬前提的东西**：

1. **`initSync` 现在跑在 LoginGate 之外、且晚于 `main.js` 的 store 写入。** 门闸和 M8 都建立在「同步发生在正确的时机」上，而当前时机是错的。方案 M1 写「视情况微调 `main.js` 启动顺序说明（未必改 store 加载本身）」——这是低估，启动顺序必须改。
2. **M8「普通退出清本机缓存」被标为「低风险」，实际是本版风险最高的一片。** 它同时踩到内存态未清、idle 自动登出、离线无缓存三个坑，其中一个会真丢账。
3. **「少 reload」这条已拍板的决定，隐含一个方案没写的工作量：把云端数据灌进 Pinia 内存。** 现状全靠 `window.location.reload()` 兜底，去掉它就必须新增 store 统一重灌。

范围**不算过重**，但**切片顺序和工作量估计需要改**。S1 比方案想的重，S5(M8) 比方案想的重得多，S3/S4 名副其实。

## 一、必须在开干前把方案补上（P0）

### P0-1 · 同步入口的时机与位置是错的，门闸和 M8 都建在上面

**代码事实**：

- `App.vue` 的模板是 `<LoginGate v-if="!isAuthenticated" /> <div v-else id="app">`，但 `initSync` 挂在 `setup()` 的 `onMounted` 里。**App 组件无论渲染哪个分支都会挂载**，所以 `initSync` → `pullOnStart()` 在「还停在 LoginGate 口令页」时就已经执行，云端账本已经落进 localStorage。
- `main.js` 里 7 个 store 的 `loadFromLocalStorage()` 和 `monthlyStatementsStore.ensureCatchUp()` 都在 `app.mount()` **之前**执行，即在 `initSync` patch `setItem/removeItem` **之前**。`ensureCatchUp()` 在跨自然月时会调 `saveToLocalStorage()` 写 `pam-monthly-statements`（`stores/monthlyStatements.js:191`）。

**两个后果**：

- **M8 是纸面安全。** 普通退出清掉本机账本 → 用户刷新页面 → App mount → `initSync` → `pullOnStart` → 本机空、`version=0`、云端 v5 → 直接 `hydrateLocal` → **账本原样回到 localStorage，而此时还没过口令页**。「退出后 F12 看不到账本」这个目标只能维持到下一次页面加载。
- **M2 会静默吃掉一次未标记的本地写入。** `ensureCatchUp` 的那次写发生在 patch 之前，**不会置 dirty**。在现状（本地为主）下无害，只是延迟到下次写才推；但 M2 翻转成「不一致就以云为准」之后，这次写会被云端静默覆盖，且没有任何冲突提示。

**建议写进方案**：

- `initSync`/`settle` 的触发点移到「通过 LoginGate 之后」（`watch(isAuthenticated)` 或在 LoginGate 成功回调里），门闸 UI 也在该边界之内；
- **localStorage 的 patch 与 settle 解耦**：patch 应在 `main.js` 最早期就装上（早于任何 store `loadFromLocalStorage`/`ensureCatchUp`），settle 才等鉴权；或把 `ensureCatchUp()` 整体后移到 settle 完成之后再跑。二选一，但必须选一个并写死。

### P0-2 · M8 的三个坑（本版风险最高的一片，不是「低」）

**(a) 只清 localStorage，不清 Pinia 内存 → 账本会被内存态复活，甚至覆盖云端。**
现状 `logout()` 只把 `isAuthenticated` 置 false，页面不 reload，App 仍挂载，**7 个 store 的内存里仍持有完整账本**。加上 M8 之后：清了 localStorage → 用户不刷新页面、直接用口令重新登录 → 界面重新渲染内存里的旧账本 → 任何一次编辑触发 store 的 `saveToLocalStorage()` → **整本"复活"写回 localStorage → dirty → 推云**。如果这中间云端已被另一台设备更新，这就是一次「用陈旧内存态覆盖云端」。
`secureLogout` 现在是安全的——因为它 800ms 后强制 `reload()` 或 `location.assign('/cdn-cgi/access/logout')`。**M8 必须让普通退出也强制重载**，否则清缓存不仅无效，还多了一条丢账路径。

**(b) 空闲自动登出会顺带清账本。**
`useIdleLogout` 15 分钟无操作调的是 **store 的 `auth.logout()`**，而 M8 计划改的是 App.vue 里的 `logout()` 包装。方案 M8 的「主要文件」同时列了 `App.vue（logout）` 和 `stores/auth.js`，这个歧义必须消掉：**清理只能挂在用户显式点击退出的路径上**。若挂进 store action，用户去吃个饭回来账本就没了，离线时更是直接进不去（见 (c)）。建议在方案里写死一句：「idle logout 不清账本，只清会话」。

**(c) 清了缓存 + 离线 → 会引导用户重新建账 → 联网后一次「用本机」就真丢账。**
`clearAllData()` 会调 `resetSyncState()`，把 `pam-sync-meta`（版本号）和 dirty 一并抹掉。于是本机彻底失忆：不知道自己曾经绑过一本云端账本。此后离线启动 → 门闸走 `offline` 分支 → 「带缓存进入」，但缓存已经没了 → `hasOpenedBooks === false` → 界面弹「尚未期初建账 · 去建账」→ 用户真去建了一遍 → dirty → 联网 → 云端 v5 > 本机 → 冲突弹窗 → 用户选「用本机」→ **真账本被一份新建空壳覆盖**。

**建议**：退出清缓存时**保留一个非账本的轻量标记**（如 `pam-cloud-bound: {email?, lastVersion, lastSyncedAt}`），门闸据此在「离线 + 无本机数据 + 曾绑定云端」时显示「账本在云端，当前离线，请联网后进入」，而**不是**建账引导。这条不做，M8 就是净负收益。

### P0-3 · 「少 reload」意味着必须新增 store 统一重灌，方案没算这笔账

第 6.4 条已拍板「优先一次 settle，尽量少整页 reload，合入后能直接进主界面就直接进」。但 `hydrateLocal()` 只写 localStorage，**Pinia 内存不会自己更新**——现状唯一的同步手段就是 `onHydrated` 里的 `window.location.reload()`。

所以 S1/S2 实际要交付的是一个 `reloadAllStores()`（7 个 store 的 `loadFromLocalStorage()` + 之后再跑一次 `ensureCatchUp()`），并保证它和 `suppressing` 标志不打架。这是 M1 里最实的一块工作量，方案正文一个字没提，只写了「hydrate 后再进主界面」。建议补进 M1，并把 `reload` 明确降级为「内存/存储不一致的兜底」。

### P0-4 · `hydrateLocal` 不是原子的，失败会留下「版本号说最新、数据其实残缺」

`hydrateLocal` 先 `removeItem` 全部 clearable 键、再逐个 `setItem`。中途抛异常（QuotaExceeded、隐私模式）时：`finally` 只复位 `suppressing`，异常向上抛给 `pullOnStart` 的 catch → 被当成「离线静默」吞掉；**而 `suppressing=true` 期间所有 remove/set 都不置 dirty**。结果本机是半清空状态、没有 dirty、下次启动若 `remote.version` 未变则不再拉——**静默数据损坏，且不可自愈**。

现状 hydrate 只在 `remote.version > local` 时发生，频率低；M2 翻转后 hydrate 会明显变频繁，这条风险被放大。建议：hydrate 包 try/catch，失败时**不写 version**、并置一个「需重拉」标记，进入时明确提示。

### P0-5 · 门闸必须有超时，否则弱网会白屏挂死

第 6.1 条「不上复杂超时框架」的判断我同意，但要区分「复杂框架」和「一个 `AbortController`」。`fetchRemote` 现在没有任何超时。断网会立刻 reject（没问题），但**弱网/DNS 黑洞/Access 跳转挂起**时浏览器 fetch 可以挂几十秒到几分钟。门闸从「等一个结果」变成「白屏等三分钟」。

`AbortController` + 8~10s 超时，约 5 行，必须有。超时按 `offline` 分支处理并给重试入口。

## 二、随 S2 一并处理（P1）

### P1-1 · M2 的「payload 指纹不同就以云为准」这个可选项，建议不要

M2 写「若本地与云端不一致（版本落后，**或可选：payload 指纹不同**），以云为准」。

「版本落后就跟云」是安全的（版本由服务端单调递增，落后即确定过时）。但「版本相同、指纹不同」意味着**本地存在没被 dirty 记录到的改动**，来源包括：P0-1 说的 `ensureCatchUp` 早期写入、`hydrateLocal` 半失败（P0-4）、dirty 键写入失败、用户手动清了 `pam-sync-dirty`。这些恰恰是「本地有真数据但系统不知道」的场景——**此时静默跟云 = 精准地覆盖掉唯一那份未记录的改动**。

建议：版本相同但指纹不同，**当异常处理**（弹冲突，或保守地推本地），不静默跟云。这个可选项从方案里划掉更省事。

### P1-2 · 冲突弹窗是盲选，而 M4 把默认按钮指向了「丢弃本机」

冲突的典型触发场景，恰恰是「本机有一批离线记的账」。M4 把主按钮设成「使用云端账本」= **默认动作是丢掉用户刚记的那几笔**。虽然有 P1-I2 的覆盖前备份兜底，但那份备份的可发现性接近零：`pam-sync-lastDiscarded` 写进了 localStorage，**全项目没有任何 UI 能把它读回来**；下载的 JSON 在 iOS 上还可能被拦。而 M8 又计划把 `pam-sync-lastDiscarded` 一并清掉。

三条建议，按性价比排序：

1. **弹窗内显示两边摘要**（条目数 / 最后更新时间 / 总资产合计）。现在弹窗只说「云端更新于 X」，用户没有任何依据做整本二选一。这是本版最值得加的一个小功能。
2. 「用云端」执行后，给一条可点击的「恢复刚才被覆盖的本机账本」入口（读 `pam-sync-lastDiscarded` 走导入路径）。备份写了却读不回来，等于没写。
3. 主按钮**不做强倾向**（两个按钮同权重），或至少在有摘要之后再谈默认项。

### P1-3 · `empty-cloud` 分支有一个未定义的死角

`pullOnStart` 里 `remote == null`（GET 404）时，只有 `hasLocalData() && (version === 0 || dirty)` 才补推。**若本机有数据、`version > 0`、且 `!dirty`（即云端账本被删过，本机自上次同步后没改过），代码什么都不做**：不推、不清、不提示，且此后永远不会再 dirty，两边永久不一致。

权威翻转后这个状态必须被明确定义。建议直接补推（本机是仅存副本，赶紧存回云），并在 M1 的状态机里把 `empty-cloud` 拆成「从未上云」和「云端消失」两种。

### P1-4 · 一批必须同步改掉的文案（否则主动误导）

- `dataReset.js:142` 安全退出对话框：「与「退出登录」不同：退出登录**不删**账本」——M8 后这句是错的。
- `App.vue:337` 普通退出提示：「已退出登录（**账本仍保留在本机**）」——同样要改。
- `docs/CLOUDFLARE.md` 心智模型（M6 已列，确认覆盖到「本机是缓存」这句）。

### P1-5 · smoke 必须硬性配套，不能「视情况补」

第 7 节只写「现有 smoke 全绿；**视情况**补」。上一轮评估（F1）的教训正是「mock fetch 从不失败 → 失败路径零覆盖 → 修了等于没修」。本版新增的每一条判定分支都在失败路径上。

建议改成硬门闩：S1 配一条「门闸各状态返回值」用例，S2 配一条「云优先 hydrate + dirty 时不跟云」用例，S5 配一条「退出清缓存后 pullOnStart 不复活账本」用例。

## 三、可缓做，但要写进已知取舍（P2）

| # | 内容 |
|---|------|
| P2-1 | **服务端 `clientVersion > server.version` 放行规则**。P1 为了掐断 I6 乒乓，让服务端接受客户端断言的更高版本并跳到 `clientVersion+1`。在「云端权威」的新语义下这条是反的——权威源不该接受客户端的版本断言。好消息是 M8 会把本机 version 清零，虚高版本的主要来源随之消失。建议改成返回 409 + `reason: 'version-ahead'`（前端另给一套文案），但要前后端一起动，本版可缓做，先记账。 |

## 四、逐条回答你点名要审的四个问题

### 1. 权威翻转是否站得住？

**站得住，但要认清它翻的是什么。**

翻转后的真实语义是：**启动那一刻以云为准；运行期仍是本地写、异步推。** 这不是「KV 成为运行期的真源」——真源在两次 settle 之间仍然是本机内存和 localStorage。这个「弱权威」对自用账本完全够用，且是把改动面控制在同步层的唯一办法，选得对。

但方案的措辞（「KV 权威源」）比实际强，容易在后续讨论里被当成更强的保证。建议在第 2 节语义表里补一句限定：「权威仅在 settle 时刻生效；运行期本地缓冲，冲突交由整本二选一」。这样 M5（回前台）为什么可以只提示不自动跟云，就自洽了。

### 2. 启动门闸与冲突策略？

**门闸的方向对，但当前设计位置错（P0-1）、缺超时（P0-5）、缺 store 重灌（P0-3）。** 补齐这三条之后，M1 是本版杠杆最高的一块，值得优先。

**冲突策略：保留「dirty + 云端更新 = 必弹窗，绝不静默覆盖」是这版最该守住的一条，同意。** 但整本二选一必须配摘要（P1-2），否则用户是在没有信息的情况下做不可逆决定。默认按钮偏「用云端」这一项，建议等有了摘要再定。

### 3. 普通退出清本机缓存、云端不删？

**「云端不删」完全同意**——防误删的价值远大于「彻底清干净」的洁癖，且 M7 已明确不做，判断正确。

**「普通退出清本机缓存」的方向也对，但按现在的方案实施会是净负收益**，三个坑见 P0-2：内存态复活（可能反向覆盖云端）、idle 自动登出误清、离线无缓存诱导重建账。补上「强制重载 + idle 例外 + 保留 cloud-bound 标记」这三条之后再做。这就是我把 S5 从「低风险」重新标为「本版最高风险」的理由。

### 4. 「本机口令可移除但本版不实施」与 Access 门禁是否匹配？

**「本版不实施」这个决定完全正确**——LoginGate 一旦拆掉，同步门闸就失去了一个天然的时机边界（P0-1），两件事缠在一起做会很难收。

**「方向可去掉」这个判断则需要加两个限定条件**：

1. **前置条件要确认并写进方案**：Access Application 必须覆盖 `/*`（含静态资源），而不只是 `/api/*`。API 侧每次请求都验 JWT，这块无懈可击；但如果页面本身不在 Access 保护内，任何人打开站点就能读到 localStorage 里的账本——那时挡住的只有 LoginGate。从 `secureLogout` 用 `/cdn-cgi/access/logout` 看应该是站点级 Access，但这是移除口令的硬前提，值得在方案里落一条确认项。
2. **两者防的不是同一件事**。Access 会话默认按天计，有效期内**同一台机器上任何人打开浏览器都能直接进**。LoginGate 是 sessionStorage（关标签页即失效）+ 15 分钟空闲登出，这层在「公共电脑 / 借出设备」场景下提供的保护 Access 给不了——而这个场景正是 `secureLogout` 对话框里白纸黑字写着的目标场景。

所以准确的表述是：**在纯自用、设备不外借的前提下，Access 足以作为唯一正门；一旦保留「安全退出清账本」所隐含的共用设备场景，口令就不该完全移除**，最多降级为可选开关。建议把这条限定补进第 6.3 条，别让「方向可去掉」在几个月后被当成已决结论直接执行。

## 五、范围与切片建议

**范围不算过重，但顺序和权重要改。** S1–S5 里没有一块是可以砍掉的（S3 同步状态 UI 看似最轻，实际是权威翻转后用户判断「我这笔存住了没有」的唯一依据，不能砍）。真正的问题是 S1 和 S5 都被低估了。

建议改成：

| 切片 | 内容 | 相对方案的变化 |
|------|------|----------------|
| **S1'** | M1 门闸 + **入口时机前移/后移（P0-1）** + **store 统一重灌（P0-3）** + **fetch 超时（P0-5）** | 明显变重，是本版主体 |
| **S2'** | M2 拉取偏好（**去掉指纹分支，P1-1**）+ M4 文案 + **冲突摘要（P1-2）** + **hydrate 原子性（P0-4）** + `empty-cloud` 分支定义（P1-3） | 略变重 |

## 六、手测门闸补充

第 7 节的 7 条都保留，建议补 5 条（都是本次发现的路径）：

## 七、结论

**批准方向，不批准按现版直接开干。**

阻塞项是 P0-1 到 P0-5 这五条，其中 P0-1（入口时机）和 P0-2（M8 三个坑）是硬阻塞——不补就会出现「M8 做了等于没做」和「离线场景真丢账」两种结果。这五条都是方案层面的补充，不需要先写代码，预计把方案改到可开干状态是一轮编辑的工作量。
