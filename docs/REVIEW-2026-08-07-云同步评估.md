范围：`functions/api/ledger/index.js`、`functions/api/_lib/accessJwt.js`、`src/utils/cloudSync.js`、`src/App.vue` 同步集成、`src/utils/ledgerBackup.js`、`src/constants/storageKeys.js`、三个 smoke 脚本。
性质：只读评估，未改动任何代码。三个 smoke 均本地跑过并全绿。

## 0. 总体判断

架构选型是对的。**版本号仲裁而非时间戳**、**localStorage 为主副本**、**不做 DELETE**，这三条决策在自用小账本的语境下都站得住脚，而且比大多数「顺手加个云同步」的实现更克制。JWT 校验的实现（零依赖、RS256、JWKS 缓存、验签后才取 email）也比常见的 `atob` 裸解 payload 要正经。

但**同步引擎缺一块**：注释里承诺的「保留 dirty，下次触发或下次启动重试」在代码中不存在。这不是风格问题，它会在 D7 的真实双设备场景里造成静默丢账。这是本次唯一的致命项。

## 一、致命（必须在 D7 前处理）

### F1 · 推云失败无重试，且下次启动会被云端静默覆盖

`cloudSync.js` 头部注释第 8 行写：

> 离线优先：推云失败不阻塞记账，保留 dirty，下次触发或下次启动重试

**全文件没有 `dirty` 变量。** `runPush()` 的 catch 只 `console.warn` 后返回，本次推送就此丢弃；`pullOnStart()` 只在 `remote.version < localVersion` 时补推，而推送失败时本地版本号根本没变（仍等于云端），所以永远走不进那个分支。

已用真实 `cloudSync.js` + mock 云端复现（脚本见附录）：

```
基线: cloud v1, A v1, B v1
① B 断网记账后: B 本地版本 = 1 （推云失败，已静默丢弃）
② B 联网重启后: cloud v1 —— B 的离线流水是否已上云?  否 ❌
③ A 记账后 cloud v2
④ B 再次启动后: B 的离线流水 = null → 静默丢失，无冲突弹窗 ❌
```

第 ④ 步是最伤的：`pullOnStart` 在 `remote.version > getLocalVersion()` 时**无条件** `hydrateLocal()`。因为没有 dirty 标记，它无从知道本地存在未上云的改动，于是把 iPad 上离线记的账直接清掉，**连冲突弹窗都不弹**——用户感知不到任何异常。

触发条件在 D7 场景里相当常见：iPad 熄屏后网络挂起、地铁里记账、Access 会话过期（见 I4）都会走到这条路径。

**修复方向**（改动面小，约 30 行）：

- 落一个持久化的 `pam-sync-dirty` 标记：`schedulePush()` 时置位并写入 localStorage，`runPush()` 成功后清除，失败则保留。
- `pullOnStart()` 开头读该标记：若 dirty 且 `remote.version > localVersion`，**不要 hydrate**，直接走 `onConflict` 弹窗，让用户二选一。
- `runPush()` 失败时排一次退避重试（例如 30s），并监听 `window.addEventListener('online', ...)` 触发补推。

风险：低。只碰 `cloudSync.js` 存取层，不涉及算账逻辑。但**必须给 smoke 补一条断网用例**，否则等于没修——现有 `smoke-cloud-sync.mjs` 的 mock fetch 从不失败，这条路径完全没有覆盖。

## 二、重要（D7 可先跑，但要排期）

### I1 · 冲突「用本地」可能谎报成功

`resolveConflictUseLocal(serverVersion)` 用弹窗弹出时记录的 `serverVersion` 去推。若用户犹豫期间另一台设备又推了一版，服务端版本已前进 → 再次 409 → 函数**静默 return**，既不更新版本也不重新通知。

而 `App.vue` 的 `chooseLocal()` 无论如何都会关掉弹窗并 `ElMessage.success('已用本地账本覆盖云端')`。用户看到成功提示，实际什么也没写上去。

同一处还有：`chooseLocal` / `chooseCloud` 都没有 `try/catch`，网络异常会抛出未捕获的 Promise rejection，弹窗卡在原地无任何反馈。

### I2 · 「用本地」是不可逆的整包覆盖，覆盖前无备份

选「用本地」意味着另一台设备那份数据被整包冲掉，无法恢复。E1 已经有 `collectLedgerData` / `downloadBackup` 的现成能力，建议在两个 `resolveConflict*` 执行前先把**将被丢弃的那一份**落成一个备份 JSON（本地下载，或写入 `pam-sync-lastDiscarded` 键）。成本很低，兜底价值高。

### I3 · `removeItem` 不触发推云，删除类操作永不上云

`initSync` 只 patch 了 `setItem`。但业务代码里存在直接 `removeItem` 业务键的路径：

- `src/stores/fundTransfer.js:188` → `FUND_TRANSFERS`
- `src/stores/openingBalance.js:64, 197` → `OPENING_BALANCE`、`MONTHLY_STATEMENTS`
- `src/utils/dataReset.js:76` → 全量 `ALL_CLEARABLE_KEYS`

这些删除不会置 dirty、不会推云。后果是本地已删、云端仍在，且本地版本号未变 → 下次启动 `remote.version === localVersion` → 不拉不推 → **两边永久不一致，静默**。

`dataReset` 的场景尤其别扭：用户「重置账本」清空本机，云端旧账本原封不动，下次换设备一拉又回来了。

修复：同样 patch `removeItem`（`hydrateLocal` 内部的 clear 已有 `suppressing` 保护，不会回环）。

### I4 · Access 会话过期 → 同步静默死掉

Access 会话过期后，`fetch('/api/ledger')` 拿到的通常不是 401，而是 **302 跳登录页**；`fetch` 默认 `redirect: 'follow'`，最终得到一个 `200` 的 HTML 响应。于是：

- `fetchRemote()`：`res.ok === true` → `res.json()` 抛错 → 被 `pullOnStart` 的 catch 吞掉（注释写「离线静默」）。
- `pushRemote()`：同样走到 `res.json()` 抛错 → 被 `runPush` 的 catch 吞掉。

用户会以为在同步，实际早就断了，而且叠加 F1 就是持续丢数据。

建议：`fetch` 加 `redirect: 'manual'`；对 401/403/opaqueredirect 与网络错误分开处理——网络错误静默重试，鉴权失效则明确提示「云同步已断开，请刷新页面重新登录」。

### I5 · KV 的 get-then-put 不是原子操作

`onRequestPut` 是「读 → 比版本 → 写」，Cloudflare KV 既不提供 CAS，读还是最终一致的（跨 PoP 传播可达数十秒）。两个后果：

- 两台设备近乎同时推送，可能都读到 v1、都写 v2，后写覆盖先写，**无 409**。
- 设备 B 刚推完 v2，设备 A 立刻 GET 可能仍读到 v1 的旧值。

单用户双设备下概率不高（人手动操作天然错开秒级），但「防抖 2s」意味着两边几乎同时保存时窗口是存在的。

这条**不建议现在改**——真要根治得换 Durable Objects 或 D1，属于架构级改动，与「自用小账本」的定位不匹配。但应该写进笔记作为**已知取舍**，并且 I2 的「覆盖前备份」正是这条的兜底。

### I6 · 版本号倒退会让冲突检测整体失效

若云端 KV 被人工清空（文档里写的「清云数据走 CF 控制台」就是这个路径），服务端从 v1 重新开始，而两台设备本地 meta 还停在 v5。此后：

- A 启动 → `remote.version(1) < local(5)` → 推 → 服务端 `clientVersion(5) >= server(1)` 通过 → 写成 v2。
- B 启动 → `remote.version(2) < local(5)` → 推 → 写成 v3，把 A 的覆盖掉。
- 两边互相覆盖、来回打乒乓，**全程不产生 409**。

根因是服务端对 `clientVersion > server.version` 无条件放行。建议：服务端遇到 `clientVersion > server.version` 时也返回 409（这在正常协议下不可能发生，出现即说明状态已错乱），让前端弹窗交给人决定。

## 四、评估结论（按第五节重点逐条）

**1. 云同步正确性（API 侧）** — 合格偏上。JWT 校验顺序正确（验签通过才取 email），409 判定逻辑本身没写错，version 由服务端单调递增的设计是对的。缺陷集中在**边界**：非原子 CAS（I5）、版本倒退放行（I6）、JSON.parse 未防御（S1）。

**2. 前端同步引擎** — **不合格，有致命项**。serialize/hydrate 的对称性是干净的（`collectLedgerData`/`replaceLedgerData` 纯函数、非 JSON 值原样保留、覆盖语义明确、`suppressing` 防回环到位，这块写得好）。但**失败路径基本没有实现**：无 dirty 持久化（F1）、无重试、`removeItem` 漏网（I3）、鉴权失效被当成离线吞掉（I4）、冲突解决会谎报成功（I1）。注释描述的行为与代码实际行为不一致，这比缺功能更危险——它会让人以为已经做了。

**3. 数据安全** — 与「无凭证、低安全需求」的既定判断一致，无异议。`.env.production` 已确认不含任何密钥；`wrangler.toml` 里的 team domain 与 AUD 都是公开标识符，放 `[vars]` 没问题。JWT 校验没有可利用的绕过面（伪造 `Cf-Access-Jwt-Assertion` 头仍需通过团队 JWKS 验签）。仅 S2/S3/S4 三处可收紧。

**4. 离线可用性** — **这是最弱的一环**，见 F1 / I3 / I4。断网记账本身没问题（localStorage 主副本的设计保证了这点），但「联网后对齐」这半程实质上缺失。

**5. 代码质量** — stores/models 分层清楚，`storageKeys.js` 作为键名单一真源是个好决策，`ledgerBackup.js` 的「纯函数 + 注入读写」让 Node 侧能直接做 round-trip 验证，这个手法值得保持。主要包袱是组件体量：`BankDepositList.vue` 1017 行、`MonthlyFinance.vue` 797 行，后续加功能会开始难受，但不是当前问题。

## 五、是否阻塞 D7？

**阻塞。一条：F1。**

理由是 D7 的验收内容恰好就是 F1 的触发场景。现在直接做双设备实测，大概率会得到「看起来通了」的结论——因为两台设备都在线、手动操作天然错开，正常路径确实能跑通（smoke 已经证明了这点）。**然后在某次 iPad 熄屏或地铁场景里静默丢掉几笔账，而且事后无从追查**，因为失败只写在 console.warn 里。

建议顺序：

1. 先做 S7（换行符归一化），让后续 diff 可读。
2. 修 F1（dirty 持久化 + 启动时 dirty 冲突分支 + online 事件补推），同时给 `smoke-cloud-sync.mjs` 补一条**断网用例**：断网记账 → 恢复网络 → 断言数据最终上云 / 或断言弹出冲突。
3. 顺手修 I3（patch `removeItem`）与 I1（冲突失败不谎报），两处都是几行。
4. 再做 D7 双设备实测，并**专门测一遍飞行模式路径**：iPad 关网记两笔 → 开网 → 确认电脑端能看到。

I4 可以放在 D7 之后，但要在实测时留意 console 有没有 `push failed`。I5 / I6 建议只写进营地笔记作为已知取舍，不动代码。

## 附录 · F1 复现脚本

复现用的是仓库里真实的 `src/utils/cloudSync.js`，只 mock 了 `fetch` 与 `localStorage`（与 `smoke-cloud-sync.mjs` 同一套手法），额外加了一个 `online` 开关模拟断网。核心断言：

```js
// ① B 断网记账 → 推云失败
online = false
lsB.setItem('pam-bank-movements', JSON.stringify([{ id: 1, desc: 'B 离线记的一笔' }]))
await sleep(2400)                       // B 本地版本仍为 1，推送已丢弃

// ② B 联网重启 → pullOnStart 不补推
online = true
await B.pullOnStart()                   // cloud 仍为 v1，离线流水未上云

// ③ A 在电脑上记一笔 → cloud v2
// ④ B 再次启动 → remote.version > local → 无条件 hydrate
await B.pullOnStart()
lsB.getItem('pam-bank-movements')       // → null，静默丢失，无冲突弹窗
```

建议把这段整理进 `scripts/smoke-cloud-sync.mjs` 作为回归用例：修好 F1 之后，第 ② 步应断言云端已含 B 的流水，或第 ④ 步应断言 `onConflict` 被调用。
