## 二、已知取舍（本批明确不做）

1. **I5 · KV 无 CAS 且最终一致**
   `onRequestPut` 的「读→比→写」非原子，近乎同时的双端推送仍可能后写覆盖先写。
   根治需换 Durable Objects 或 D1，属架构级，与「自用小账本」定位不匹配。
   兜底：冲突覆盖前双向备份（I2）。

2. **`runPush` 空数据不推云**
   本地账本为空时直接 `clearDirty()` 返回，不推云。这是**刻意行为**，与「不做 DELETE、防误删」一致：
   本机清空不会传播成云端清空。配合重置语义 A（清 sync-meta）→ 下次启动云端账本同步回来。

3. **前台拉取的两次刷新**
   提示条 → 点刷新 → remount → 后台 `pullOnStart` 才 hydrate + reload，约 1 秒内两次闪屏。
   换来的是「不会在用户填表时改存储」，判定为可接受。

4. **epoch 世代标识（未做，另开条目）**
   服务端约 8 行 + 客户端约 3 行：首写时生成 `epoch`，客户端存进 sync-meta 并随 PUT 带回，
   `client.epoch !== server.epoch` → 409。可识别「人工清空 KV」「换 KV namespace」「从备份恢复」等
   纯版本号无法区分的分叉。**当前限制**：人工清空 KV 后需手动确认两台设备状态
   （`Math.max` 已终止乒乓覆盖，但先推的那台的增量可能被后推的静默顶掉）。

5. **S8 · hydrate 与 reload 之间的窗口**
   启动路径 hydrate 后立即 `window.location.reload()`，窗口极短；前台路径已改为不写存储，
   该风险面进一步收窄。未做额外处理。

### smoke-access-jwt 用例顺序的约束（重要，勿随意调整）

强制刷新 JWKS 带 60s 冷却，**整个进程只允许触发一次**。因此：

- 「密钥轮换」用例（要求刷新**发生**）必须排在
- 「篡改签名」用例（要求刷新被冷却**挡下**）之前

交接稿原方案把篡改用例留在轮换之前，会先把冷却额度用掉，导致轮换用例的
`jwksFetchCount === countBefore + 1` 断言失败。已调整为 1–8 早退用例 → 9 轮换 → 10 篡改+冷却。
其余用例都在验签之前返回，不消耗冷却额度。

## 四、环境事故记录

**Linux 沙箱对 Windows 挂载盘做 webpack 构建不可行。**

- 跨挂载的单次 `stat` 约 3.2ms，沙箱本地盘约 0.03ms，**慢约 100 倍**
- `node_modules` 50,477 个文件，webpack 解析要做十万级文件操作 → 构建 25 分钟未完成
- `dist/` 下 unlink 报 `EPERM`，`.git/` 下同样只能创建不能删除

**结论**：`npm run build` 与 `git commit` 都应在 Windows 侧执行；沙箱只适合跑纯 Node 的 smoke 与 eslint。
